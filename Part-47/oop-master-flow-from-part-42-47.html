3 Why the word "Procedural"?

Hard word, simple meaning.

Procedure = a set of step-by-step actions (like a recipe). So in Road 1 the program is built around actions. Data just travels into functions.

📘 For your exam: Python is not "only procedural." It is a multi-paradigm language — it supports procedural, object-oriented and functional styles. "Procedural" is a style, not the whole language.
Hold this difference

Procedural = built around actions.
OOP = built around things (objects) that carry their own actions.

4 So what exactly is a class?

Before we ask "why" — first, what is this word?

So far we built everything with functions. For bigger programs Python gives us a second tool: the class. The word sounds scary, so let's remove the fear first.

class is not a Python invention. It is a Computer Science word, older than Python — from the language Simula in 1967. It simply means "a kind / a category of thing." Java and C++ have classes too — Python only borrowed the idea.

A class lets you build your own kind of thing that can hold its data, its actions, and its rules together under one name.

One class holds data, actions and rules together as a single named unit.
⚠ You'll hear many definitions: "a class is a blueprint," "a template," "a real-world thing." These are hints, not the answer. The precise, provable truth — coming up in a few steps — is simpler: a class lets you create your own data type, one Python treats exactly like int, str or list.
📘 Textbook word (preview): a custom type like this — data bundled with the operations on it — is the start of what books call an Abstract Data Type (ADT). We'll see why it's called "abstract" once we hide the internals behind methods (§21).
So the next question is…

We already have functions. Why do we even need this new "kind of thing"?

5 So why do we need classes?

Functions are great — but they have one big pain.

A function is a machine: input → output → then it forgets everything. It keeps no memory between calls. The secret is where the = 0 runs:

✗ Function — forgets every call
python
def deposit(amount):
    balance = 0           # re-made as 0 EVERY call
    balance += amount
    return balance

print(deposit(500))   # 500
print(deposit(500))   # 500 ← forgot the last one!
✓ Object — remembers
python
class Account:
    def __init__(self):
        self.balance = 0  # runs ONCE, at creation

    def deposit(self, amount):
        self.balance += amount   # updates stored value
        return self.balance

acc = Account()
print(acc.deposit(500))  # 500
print(acc.deposit(500))  # 1000 ← remembered!

Same = 0 — but in the function it re-runs every call (reset). In the object, __init__ runs once; after that the balance lives inside acc and survives.

That is the first reason for a class: an object keeps its own data alive. There is a second reason too — its data, actions and rules all stay together and protected.

The spine of all software

Every real thing = DATA + ACTIONS + RULES, kept together.
A bank account = balance (data) + deposit / withdraw (actions) + "never go below 0" (rule).

Functions keep these three apart, and nothing enforces the rule. Compare:

✗ Functions only (procedural)
python
# DATA sits loose, on its own
balance = 1000

# ACTIONS sit elsewhere, separate
def deposit(bal, amount):
    return bal + amount

def withdraw(bal, amount):
    return bal - amount

# carry balance in & out — it won't remember
balance = deposit(balance, 500)
balance = withdraw(balance, 2000)

# NOTHING protects the data:
balance = -9999      # allowed
balance = "oops"     # allowed!
✓ With a class
python
class BankAccount:
    def __init__(self, balance):
        self.balance = balance    # DATA inside

    def deposit(self, amount):    # ACTION with data
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:  # RULE built in
            raise ValueError("Not enough money")
        self.balance -= amount

acc = BankAccount(1000)
acc.deposit(500)         # action lives with data
acc.withdraw(9000)       # blocked by the rule ✋

Left: data, actions and rules scattered — nothing is guarded.  Right: all three bundled into ONE safe thing, rule enforced.

The pain of functions, in one line

A function only ever acts on types that already exist — int, str, list. It can never add a new one.
A function gives you a verb (an action); only a class can give you a new noun — a brand-new data type.

6 First — object vs type vs data type

This is the exact spot students get lost. Let's settle three words for good: object, type, data type.

Back in Part 8 we proved a rule that never breaks: every object is exactly three things — an identity, a type, and a value. The methods are not a fourth part of the object. They live inside the type — written once, shared by every object of that type.

Read it top-down. The object = identity + type + value. Open the type and you find "what kind" + the methods — shared, never copied into each object.

So the three words, settled once and for all:

  • Object = one real thing living in memory = identity + type + value (e.g. this one list, [1, 2, 3]).
  • Type = the "what kind?" answer = the category that holds the shared methods (here, list).
  • Data type = just another name for type — it stresses "a kind of value + the operations you may do on it." So type = "what kind" = data type. Same idea, three names.

Say it in one breath: the object holds identity + type + value; the methods live in the type. dir(x) always prints the full menu a type offers.
★ So what must OUR own type produce?

Exactly the same: objects with their own type, identity and value — plus the methods we add.
That is the whole job of class. (Even an empty class hands you real objects with type + identity + value.)

7 How to build one — in 4 tiny steps

We grow the class one line at a time. Nothing magic.

1
Name the new kind of thing
class BankAccount: — tell Python "a new type is coming."
2
__init__ — give each one its starting data
Runs automatically the moment an object is made, and fills in its data. (Python actually creates the empty object one step earlier, via __new__ — but you rarely touch it, so we unpack it in §11.)
3
self — means "this particular object"
So each account stores its own owner and balance, never mixed with others.
4
Methods — the actions, with the rule inside
Functions written inside the class. The rule ("never below 0") lives right here.
python · the whole thing, put together
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner            # data
        self.balance = balance        # data

    def deposit(self, amount):        # action
        self.balance += amount

    def withdraw(self, amount):       # action + rule
        if amount > self.balance:
            raise ValueError("Not enough money")
        self.balance -= amount

acc = BankAccount("Alice", 5000)   # __init__ runs here, automatically
acc.deposit(500)
print(acc.owner, acc.balance)        # Alice 5500
💡 Small but important: people call __init__ the "constructor." It is really the setup / initializer — the object already exists when it runs. (Full reason in §11.)

10 What really happens when you write class

Myth: "class is just a declaration." Truth: it is live code that builds an object.

When Python reaches a class block, it does not just "remember a template." It runs the indented lines top-to-bottom, gathers everything you defined into a little dictionary, and hands that to a built-in factory called type. That factory manufactures a class object and stores it under the name you chose. So Dog is a real object you just built — a class object.

⚠ First untangle this — type wears TWO hats

The same word type does two different jobs, and mixing them up is the whole confusion:
• ONE argument → type(rex) asks "what kind is this?" → answers Dog.
• THREE arguments → type("Dog", (), {...}) builds a brand-new class.

Hat 1 — three arguments: build a class

These two snippets are exactly the same. The friendly class syntax on the left is just a shortcut for the factory call on the right:

python · the class keyword is sugar for a type(...) call
class Dog:              # the friendly way you always write
    legs = 4

# ...Python quietly does THIS behind the scenes —
# it calls the `type` factory with three arguments:
Dog = type("Dog", (), {"legs": 4})

Those three arguments are simply the three things every class needs:

"Dog"
the name — what the class will be called
()
the parents — classes to inherit from (empty = none)
{"legs": 4}
the body — its attributes & methods, as a dict

Hat 2 — one argument: ask what made it (and prove it's all objects)

Now ask the other question. Since Dog was stamped out by the type factory, asking its kind returns type. Every line below is something you can run and check for yourself:

python · proof you can run yourself
rex = Dog()

# ── ask "what kind?" — climb one floor up each time ──
print(type(rex))              # <class 'Dog'>    rex was made by Dog
print(type(Dog))              # <class 'type'>   Dog was made by type
print(type(int))              # <class 'type'>   int, str, list… all made by type
print(type(type))             # <class 'type'>   type is made by type — the top floor

# ── prove a class really IS an object ──
print(isinstance(Dog, type))      # True   Dog is an instance of type
print(isinstance(type, object))   # True   even type is a plain object

# ── prove 'class' is only sugar: both build the same thing ──
class A: x = 1
A2 = type("A2", (), {"x": 1})
print(A().x, A2().x)           # 1 1   identical behaviour

🍪 The analogy that makes it click: a class is a cookie-cutter that stamps out cookies (objects). 📘 Why this matters: because a class is a normal object, you can put it in a variable, pass it to a function, build one on the fly, or let a decorator / metaclass tweak it before use (§30). Nothing about class is magic — it is a function call with nicer syntax.

11 __init__ vs __new__ — initializer, not constructor

The most common interview "gotcha."

People call __init__ the constructor. Not quite. __new__ creates the empty object; __init__ only fills the object that already exists.

flowchart LR A["you create an object"] --> N["__new__
makes the empty object"] N --> I["__init__
fills owner and balance"] I --> R["ready to use"] classDef s fill:#1a2030,stroke:#4dabf7,color:#8ec4ff; classDef d fill:#11211a,stroke:#51cf66,color:#9be7ab; class A,N,I s; class R d;
__new__ builds it · __init__ sets it up. You almost always write only __init__.
📘 Proof: __init__ must return None and it receives an already-built self. A true constructor returns the new object — that is __new__'s job.

12 self is not magic, and not a keyword

Once you see this, self stops being scary forever.

When you write acc.deposit(500), Python quietly turns it into BankAccount.deposit(acc, 500). The object simply becomes the first argument. We name that first argument self — by convention, not by law.

python · these two lines do the same thing
acc.deposit(500)              # the normal way
BankAccount.deposit(acc, 500)   # exactly the same call

# "self" is only a name. This even works (please don't):
def deposit(this, amount): ...    # still valid
📘 Why explicit? Python's rule is "explicit is better than implicit." Other languages hide this; Python shows it, so there is never any doubt which object you are touching.

13 Instance data vs class data (and a famous trap)

Where exactly does an attribute live?

Data set with self.x = ... lives on that one object. Data set directly in the class body is shared by all objects.

python
class Dog:
    species = "Canis"          # class data — shared by all dogs
    def __init__(self, name):
        self.name = name        # instance data — one per dog

a, b = Dog("Rex"), Dog("Bruno")
print(a.name, b.name)       # Rex Bruno   (different)
print(a.species)            # Canis       (shared)
⚠ The trap (same bug family as Part 25's mutable default)

A mutable class attribute is shared. tricks = [] in the class body → every dog shares ONE list.
Fix: put per-object state in __init__ → self.tricks = [].

14 Three kinds of methods — and why one isn't enough

First clear up the word, then the real question: why did Python add three kinds when a normal one already works?

📘 Function vs method: a function stands alone (deposit(...)); a method lives inside a class and is called on an object (acc.deposit(...)). Every method is a function — it just belongs to an object.

Why three, then? Because not every action needs the same things. Ask one question — what does this function need to do its job? — and the answer picks the kind:

The three kinds exist because a function may need this object, the whole class, or neither.
python · one BankAccount — all three kinds, and every reason to use a classmethod
class BankAccount:
    bank_name = "OnePercent Bank"     # class data — shared by EVERY account
    interest_rate = 5                  # class data — shared by EVERY account
    count = 0                          # class data — how many exist so far

    def __init__(self, owner, balance):
        self.owner = owner             # instance data — one per account
        self.balance = balance
        BankAccount.count += 1         # each new account bumps the shared counter

    # ── INSTANCE · needs THIS account (self) ──
    def deposit(self, amount):
        self.balance += amount         # change ONE account's own data

    # ── CLASS · needs the class (cls), not one account ──
    @classmethod
    def savings(cls, owner):           # reason 1: another DOOR to create one
        return cls(owner, 0)               # cls(...) == BankAccount(...) → new object

    @classmethod
    def from_record(cls, line):        # reason 1: yet another door — "Alice,5000"
        owner, balance = line.split(",")
        return cls(owner, int(balance))

    @classmethod
    def set_interest_rate(cls, rate):  # reason 2: a setting shared by ALL accounts
        cls.interest_rate = rate

    @classmethod
    def total_accounts(cls):           # reason 3: a fact about the WHOLE class
        return cls.count

    # ── STATIC · needs neither self nor cls ──
    @staticmethod
    def is_valid_amount(amount):        # just numbers in → answer out
        return amount > 0


# ① create FIRST …
alice = BankAccount.savings("Alice")   # classmethod opens a fresh account
# ② … THEN use
alice.deposit(500)                       # instance method needs an existing account
print(alice.balance)                    # 500

BankAccount.set_interest_rate(7)         # affects EVERY account at once
print(BankAccount.total_accounts())    # 1 — a fact about the class
BankAccount.is_valid_amount(500)          # True — no account needed

🏦 Create FIRST, then use

You can't deposit into an account that doesn't exist — open it first. Python forces the same order.

python
alice.deposit(500)                       # ❌ NameError — no account yet
alice = BankAccount.savings("Alice")   # ① open it → now it exists
alice.deposit(500)                       # ② now it works

deposit needs self — a real account. The @classmethod is the opening step (cls), so it needs no account yet.

🎯 self / cls — written, never passed. They come from before the dot: BankAccount.savings("Alice") runs as savings(BankAccount, "Alice") — the thing before the dot fills the first slot (just like acc.deposit(500) in §12).
🔑 () = make a new one · . = reach into an existing one. So cls(owner, 0) builds an account (it's just BankAccount(...)); cls.interest_rate = rate only changes shared data — the twin of self.balance += amount.
🧠 Hook: self → this one account · cls → the whole bank · no first word → a calculator inside the class.
🧩 Three kinds, not more. instance / class / static are the only ways a method binds — the list is complete. Dunder (__str__…), @property, @abstractmethod aren't a fourth kind — they're flavors on top, covered later (§22 · §28, §16 · §27, §21 · §31).
🏁 Checkpoint — your tool is ready

A class lets you create your own data type: a thing that keeps its own data, carries its own actions, guards its own rules — and remembers. One design, many objects. You have seen what it is, how to build it, and what Python does underneath.

But a tool by itself doesn't build a skyscraper — you need principles for using it well as your program grows huge. That is exactly what OOP is: a set of proven ideas for organizing classes so your app stays clean and scalable. We have forged the tool. Next, we pick it up and learn the four pillars that turn "I can write a class" into "I can design a large, professional system."

16 Pillar 1 — Encapsulation

Pain: anyone can reach in and break the data.

Our class had a rule inside withdraw. But nothing stops someone writing acc.balance = -9999 directly, skipping the rule. So we hide the data and let people touch it only through safe methods.

flowchart LR U["outside code"] -->|allowed| M["methods
deposit · withdraw"] M --> D["_balance
hidden data"] U -.->|blocked| D classDef u fill:#161b22,stroke:#33415a,color:#cdd6e0; classDef m fill:#11211a,stroke:#51cf66,color:#9be7ab; classDef d fill:#2a1416,stroke:#ff6b6b,color:#ffb3b3; class U u; class M m; class D d;
The data sits behind a wall. The only doors are the methods.

So we do two things: hide the data (rename balance → _balance) and expose only safe doors. First, the way you already know — a plain method:

python · a wall around the data
class BankAccount:
    def __init__(self, balance):
        self._balance = balance        # _ means "internal — don't touch directly"

    def withdraw(self, amount):
        if amount > self._balance:
            raise ValueError("Not enough money")
        self._balance -= amount

    def get_balance(self):            # a plain instance method — needs ()
        return self._balance

acc = BankAccount(1000)
acc.withdraw(200)
print(acc.get_balance())   # 800 — safe, but the () feels clunky

Meet @property — a method that looks like an attribute

We would rather write acc.balance — like plain data — than call the get_balance() method we just wrote above (it's ours, not built in). That is exactly what @property gives you: a method wearing the costume of an attribute. You write acc.balance with no parentheses, but a method quietly runs underneath — so every read (and, with a setter, every write) can still be guarded. (This is one of the "flavors" we flagged in §14 — underneath, it is still an instance method.)

python · read like data, write with a guard
class BankAccount:
    def __init__(self, balance):
        self._balance = balance

    @property                     # READ:  acc.balance        (no parentheses)
    def balance(self):
        return self._balance

    @balance.setter               # WRITE: acc.balance = 3000  (checked first)
    def balance(self, value):
        if value < 0:
            raise ValueError("Balance cannot be negative")
        self._balance = value

acc = BankAccount(1000)
print(acc.balance)     # 1000 — reads like data, runs a method
acc.balance = 3000     # ✓ goes through the setter
acc.balance = -100     # ✗ ValueError — the wall holds
🍽️ Like a display counter: from outside you seem to just grab the item (an attribute); really a staff member hands it over through a controlled window (a method) — the ease of "just grab it" with the safety of "staff controls it." (The @ is a decorator — a label that changes how a method is used; full story in §25.)
🔑 The big win: start with a plain public self.balance, then later upgrade to a guarded @property — and no calling code changes. acc.balance still works; only the protection is added underneath.

Two rules that trip everyone up

A property can also be computed from other fields. Watch the name rule and the one-value rule:

python · one value in, unpack inside
class Person:
    def __init__(self, first, last):
        self.first = first
        self.last  = last

    @property                        # READ:  p.full_name  (no parentheses)
    def full_name(self):
        return f"{self.first} {self.last}"   # built on the fly — nothing stored

    @full_name.setter                # name MUST match the property → full_name
    def full_name(self, value):        # a setter always gets exactly ONE value
        self.first, self.last = value.split(" ")   # split the one string into two

p = Person("Ada", "Lovelace")
print(p.full_name)             # Ada Lovelace
p.full_name = "Grace Hopper"     # one string in → becomes first + last
🧩 Three rules to remember: ① the setter's name must match the property → @full_name.setter (if it were price, it'd be @price.setter). ② A setter gets exactly one value — it's triggered by name = value. Need several? pass a tuple and unpack, or just use a normal method like set_limits(low, high) called with (). ③ Getter and setter are both instance methods (they carry self) — @property is only a costume over them.
🚪 Leave the setter out → the property is read-only. Assigning to it (p.full_name = "X") then raises AttributeError.

The three access levels (by naming convention)

Python has no private / public keyword. The name signals the intent:

LevelHow you write itWhat it means
publicbalanceanyone may use it — the official API
protected_balance"internal, please don't touch" — a polite signal only
private__balancename-mangled to _BankAccount__balance — hidden, not locked
python · proof — there is no true "private"
class Account:
    def __init__(self):
        self.owner = "Alice"     # public
        self._pin = 1234         # protected (convention)
        self.__secret = "x"      # private (name-mangled)

a = Account()
print(a.owner)             # Alice        ✓
print(a._pin)              # 1234         ✓ works, but you shouldn't
# print(a.__secret)        # AttributeError!
print(a._Account__secret)  # 'x'          ← still reachable via the mangled name
📘 Textbook word — encapsulation: keep data and the rules that guard it together, and hide the inside.
🐍 Python's twist — there is no real "private": one underscore _balance means "please don't touch." Two underscores __balance triggers name-mangling — Python renames it to _BankAccount__balance, a speed bump, not a lock. Python trusts you: here encapsulation is a clear signal, not a hard wall.

17 Pillar 2 — Inheritance

Pain: two types share 90% of their code. Copy-paste is a trap.

A SavingsAccount is a BankAccount — plus a little extra. Instead of copying, the child inherits everything from the parent and adds only what is new.

flowchart TD P["BankAccount · parent
balance · deposit · withdraw"] --> C1["SavingsAccount
+ add_interest"] P --> C2["CurrentAccount
+ overdraft"] classDef p fill:#241a05,stroke:#ffd43b,stroke-width:2px,color:#ffd43b; classDef c fill:#1a2030,stroke:#4dabf7,color:#8ec4ff; class P p; class C1,C2 c;
Write the shared part once in the parent. Children get it for free.
python · reuse, do not copy
class BankAccount:
    def __init__(self, balance):
        self.balance = balance
    def withdraw(self, amount):
        self.balance -= amount

class SavingsAccount(BankAccount):    # inherits everything
    def add_interest(self):              # adds something new
        self.balance += self.balance * 0.05

s = SavingsAccount(1000)
s.add_interest()    # new ability
s.withdraw(200)     # reused from parent
print(s.balance)    # 850.0
🔌 Python already does this: bool inherits from int — that is why True + True == 2. Proof: issubclass(bool, int) → True.

Going deeper — overriding & super()

A child can override a parent's method — write its own version — and still call the parent's with super(). The most common use is __init__: the child sets up its own extra data, then lets the parent set up the rest.

python · override, and reuse the parent with super()
class SavingsAccount(BankAccount):
    def __init__(self, balance, rate):
        super().__init__(balance)      # reuse parent setup → sets self.balance
        self.rate = rate               # then add the child's own extra

    def withdraw(self, amount):        # OVERRIDE the parent's method
        print("audit log...")       # add new behaviour
        super().withdraw(amount)     # then reuse the parent's version

But what is super()? It does not mean "the parent." It means "the next class one step up the chain." Each call hops exactly one level — so if you stack three levels, the calls climb the ladder one rung at a time:

python · super() climbs ONE level per call
class BankAccount:                       # level 1 — the root
    def __init__(self, balance):
        self.balance = balance
    def describe(self):
        return f"balance={self.balance}"

class SavingsAccount(BankAccount):       # level 2
    def __init__(self, balance, rate):
        super().__init__(balance)         # one step up → BankAccount
        self.rate = rate
    def describe(self):
        return super().describe() + f", rate={self.rate}%"       # up → BankAccount

class PremiumSavings(SavingsAccount):    # level 3
    def __init__(self, balance, rate, cashback):
        super().__init__(balance, rate)   # one step up → SavingsAccount
        self.cashback = cashback
    def describe(self):
        return super().describe() + f", cashback={self.cashback}%"  # up → SavingsAccount

p = PremiumSavings(1000, 5, 2)
print(p.describe())
# balance=1000, rate=5%, cashback=2%   ← the whole chain ran, one hop at a time
🪜 One rung per call. PremiumSavings → SavingsAccount → BankAccount. A single super() jumps one level up — never straight to the top. Because each level calls super() again, the calls chain up: the root runs first (balance=1000), then each child appends its part as the calls return.
❗ Myth: "super() = the parent." True only for a single, straight chain. With multiple parents, super() follows the MRO — the next class in line, which can be a sibling, not the literal parent (see §18).
🎯 Why not just write BankAccount.__init__(self, …)? Hard-coding the parent's name breaks the moment you rename or reorder parents, and it misbehaves under multiple inheritance. super() always picks the correct next class for you.
📘 MRO (Method Resolution Order) = the exact list Python searches. See it with PremiumSavings.__mro__.   ⚖️ Composition vs inheritance: inheritance = "is-a" (SavingsAccount is a BankAccount); composition = "has-a" (an Account has a Logger). For most real systems, prefer composition — it bends without breaking.
🧭 The word "override" — just enough for now: a child rewriting a method it inherited (our SavingsAccount.withdraw above). That's all you need here. It's really a form of polymorphism, so its full story — and its easily-confused twin overloading — comes right after Pillar 3 → §20.

The "diamond problem" — and how MRO solves it

When D inherits from both B and C, and both came from A — whose greet() wins? Other languages ban this to avoid the confusion. Python answers it with a fixed, predictable order:

python · multiple inheritance + the diamond
class A:
    def greet(self): return "A"
class B(A):
    def greet(self): return "B"
class C(A):
    def greet(self): return "C"
class D(B, C):     # multiple inheritance (the diamond)
    pass

print(D().greet())   # 'B'   ← MRO picks B (left before right)
print([c.__name__ for c in D.__mro__])
# ['D', 'B', 'C', 'A', 'object']   ← the exact, predictable search path
📘 Why some languages refuse multiple inheritance: without a clear rule, "which parent wins?" is ambiguous and bug-prone. Python's C3 rule guarantees a consistent order where every class is visited once — so multiple inheritance is safe if you keep it simple. 🧩 Mixins (small add-on classes) are the common, healthy use.
🔬 Python vs Java, at a glance: multiple class inheritance → Python ✓, Java ✗ (interfaces only). Method overloading → Python ✗ natively (last def wins — §20), Java ✓. Overriding → both ✓. So it cuts both ways: each language allows something the other does not.

19 Pillar 3 — Polymorphism

Pain: you keep writing if type == ... ladders.

"Poly" = many, "morph" = forms. One action name, and each type answers it its own way. You make the same call without caring which type it is.

Same call, different answer — no if-ladder needed.

🦆 Duck typing (Python's style): "If it walks like a duck and quacks like a duck, it's a duck." Python never checks the type — it just calls .speak(). If the object has that method, it works. No interface keyword needed (unlike Java).

20 Overriding vs Overloading — two words people mix up

Both live under polymorphism. One Python loves; the other it does not do the usual way.

Overriding — child replaces a parent's method ✓ (Python loves this)

This is runtime polymorphism: the child redefines a method it inherited. The object's real type decides which version runs.

python · the child's version wins
class Animal:
    def speak(self): return "some sound"

class Dog(Animal):
    def speak(self): return "Woof"    # OVERRIDE the parent

print(Dog().speak())   # Woof  ← child's version runs at runtime

When: you inherit something but need to change/extend its behaviour (use super() to also keep the parent's part).

Overloading — same name, different parameters ✗ (not native in Python)

In Java/C++ you can write two methods with the same name and different arguments. In Python the last one simply replaces the earlier one — because methods live in a dict keyed by name, and types are only known at runtime.

python · the second add() overwrites the first
class Calc:
    def add(self, a, b):        # this one is forgotten...
        return a + b
    def add(self, a, b, c):     # ...only THIS one survives
        return a + b + c

Calc().add(1, 2)   # TypeError: missing argument 'c'

The Pythonic ways to get "one name, many input shapes":

python · default args · *args · singledispatch
# 1) default arguments
def add(a, b, c=0): return a + b + c

# 2) *args — any number of values
def add(*nums): return sum(nums)

# 3) dispatch by TYPE (functools, PEP 443)
from functools import singledispatchmethod
class Printer:
    @singledispatchmethod
    def show(self, x): print("other:", x)
    @show.register
    def _(self, x: int): print("int:", x)

21 Pillar 4 — Abstraction

Pain: too many messy details to think about.

You press a button and the work happens — you do not see the wiring. Abstraction means: show a simple surface, hide the complex inside.

acc.deposit(500)"] --> S["simple surface

validate · update · log · notify"] classDef y fill:#1a2030,stroke:#4dabf7,color:#8ec4ff; classDef s fill:#11211a,stroke:#51cf66,color:#9be7ab; classDef h fill:#161b22,stroke:#33415a,color:#a6b3c4; class YOU y; class S s; class H h;

Easy way to remember the difference

Encapsulation = protect the data (build the wall).
Abstraction = hide the complexity (show one simple button).

The idea behind it — the interface

Every abstraction has a surface you are allowed to touch: the list of methods you may call. That list is the interface — think of it as a menu. It names the actions (speak(), deposit()); it never shows how they are cooked. The interface is the "what"; the hidden code is the "how."

🍽️ Interface = the menu. Abstraction = ordering off it without seeing the kitchen. A TV remote is an interface too: the buttons say what you can do, never how the TV works inside.

Writing that menu down so Python enforces it is exactly what an Abstract Base Class does. Same Dog and Cat from Pillar 3 — but now every animal is guaranteed to carry speak():

python · the interface, written down and enforced
from abc import ABC, abstractmethod

class Animal(ABC):            # the interface = the menu of required actions
    @abstractmethod
    def speak(self): ...      # the "what" — no "how" here

class Dog(Animal):
    def speak(self): return "Woof!"

class Cat(Animal):
    def speak(self): return "Meow!"

print(Dog().speak())   # Woof!
print(Cat().speak())   # Meow!

class Snake(Animal): pass    # forgot speak()
# Snake()  ->  TypeError at creation: must implement speak()
The interface (Animal) lists the action; each subclass supplies the hidden how. Forget it, and Python blocks the object at birth — not later at runtime.
🦆 This is the fix for duck typing: in Pillar 3 we just hoped every object had speak() — a wrong one failed late, when the method was finally called. The interface above guarantees it up front, so a missing speak() is caught the instant the object is built.
🔌 You already used it: [3,1,2].sort() sorts your list — you never wrote the sorting algorithm. That detail is abstracted away.
📘 The word from §4, now earned: a type defined by what operations it offers while its internals stay hidden is an Abstract Data Type (ADT). "Abstract" = you call acc.deposit(), never touch the raw balance. Python's own list and dict are ADTs — you never see the C array or hash table inside.
📘 Going further — Abstract Base Class (ABC): Python's abc module lets you say "every payment type must have a pay() method" and refuse to build any subclass that forgets it. It turns "please follow this shape" into an enforced rule.
⚠ Don't confuse the two: an ADT is a concept (almost every well-designed class is one); an abstract class / ABC is a specific Python feature. They share the word "abstract" but are not the same thing.
The one sentence that ties the pillars together

A class makes a new type. An object is one real thing of that type.
Encapsulation, inheritance, polymorphism, abstraction keep many objects clean — and that whole way of working is OOP.
