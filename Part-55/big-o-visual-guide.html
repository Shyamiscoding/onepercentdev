Chapter 1 · Vocabulary you need first

What does the word "complexity" actually mean?

The word "complexity" sounds advanced. It isn't. In computer science it has one very small meaning:

The one-sentence definition Complexity = how much extra work (steps) and extra memory (bytes) your code needs when the input gets bigger. Not "how complicated the code looks." Just: when I feed the code 10× more data, does it need 10× more work, 100× more, or does it stay flat?

Two flavours — that's the whole vocabulary

Time complexity how the number of steps grows with input
Space complexity how the amount of memory grows with input

Same notation, same rules, same intuition for both. Learn one, you learn the other.

Where does the word "complexity" come from? In everyday English "complex" means complicated. In computer science the word came from Latin complexus — "woven together". Mathematicians needed a term for how one quantity (steps, memory) is woven together with another (input size) — how one grows when the other grows. They picked "complexity". So when you hear the word in this chapter, think growth relationship, not "how complicated the code looks".
And why the word "time"? Why not "operations complexity"? Good question — because we're not measuring seconds. "Space" is easy: it literally means memory (bytes of RAM). "Time" is the misleading one — the label survived from the 1960s when researchers actually timed algorithms on one specific machine. The moment a faster CPU appeared that number was useless, so the field switched to counting operations (steps) instead — because every step takes some tiny amount of time on any CPU, and more steps always means more elapsed time. The name stuck, the measurement got machine-independent. So mentally read "time complexity" as "how the number of steps my code performs grows with the input". That's what it answers in one line: is my algorithm capable of handling the input as it grows, or does it collapse under real data?
Key: complexity is a property of the CODE — not the machine Your friend's M5 MacBook runs the same script 10× faster than your 2015 laptop. Same code → different seconds. So we can't describe code by "seconds" — that number depends on the machine. What we CAN describe is the growth pattern: if 10× data means 100× time on your laptop, it also means 100× time on every other machine. That growth pattern is the complexity.

Time complexity is not speed — the mind-shift that changes everything

The biggest wrong idea in this whole topic. Fix this one and everything else clicks.

The myth to unlearn Wrong: "Time complexity = how fast my code runs."
Right: "Time complexity = how the number of steps my code takes GROWS as input grows."
Speed is measured in seconds (a machine property). Complexity is measured in growth (a code property).

The thought experiment — three machines, one function

Run the same function on three machines. Then feed it 10× more data:

MachineTime for 1,000 itemsTime for 10,000 itemsRatio
Your 2015 MacBook5 s500 s100×
Friend's 2026 M5 Mac0.5 s50 s100×
An AWS server2 s200 s100×
Look at that last column Absolute seconds are all different — that's speed, and it depends on the machine. But the ratio is identical on every machine: 10× input → 100× time. That ratio IS the complexity. Big-O gives us the shorthand: this pattern is called O(n²).

Mind-shift: stop asking "how fast is this code?" Start asking "how does this code GROW?" (Remember from S1 — "time" here means growth in the number of steps, not seconds.)

Space complexity — same mind-shift, for memory

Same idea as time complexity — swap "steps" for "bytes of memory". If 10× input needs 10× RAM, that pattern is O(n) space. If it needs 100× RAM, that's O(n²) space. Growth pattern, not absolute bytes.

Memory is the harder wall — it doesn't slow down, it CRASHES Your laptop has ~16 GB of RAM. A cloud VM might have 64 GB. Neither has a terabyte. If your algorithm has O(n²) space and someone hands you n = 100,000 → that's 10¹⁰ cells × 8 bytes = 80 GB of RAM needed. Your code doesn't run slowly. It dies instantly with MemoryError. That's why space complexity isn't optional.
O(1) spacea few variables — never grows
O(log n) spacerecursion depth — grows very slowly
O(n) spacea copy of the input — usually fine
O(n²) spacea full matrix — crashes on real data
Answer as a PAIR — always When asked "what's the complexity?", the strong answer is "O(?) time AND O(?) space". Both halves. They're independent — code can be O(n) time / O(1) space (scan with counters), or O(n²) time / O(1) space (nested loops with no extra storage), or O(n) time / O(n) space (building a set). Naming both = senior-level answer.

The alphabet decoded — n, log n, n², 2ⁿ, n! in plain English

These scary symbols are just shorthand for concrete counting ideas. Translate them once and they stop being math — they become descriptions of what your loops actually do.

What is n? n = the size of your input. A list of 500 numbers → n = 500. A JSON with 10 million rows → n = 10,000,000. A 42-character string → n = 42. Whatever you're looping over, that's your n.

Now translate every Big-O you'll ever see

Symbol Plain-English meaning Code that looks like this
O(1)
say "oh of one"		 Constant. Same number of steps no matter how big n is. 1 step for 10 items, 1 step for 10 billion. dict[key] · list[i]
O(log n)
say "oh log n"		 Halving. Each step throws away half the remaining data. n = 1M → only ~20 steps. Binary search on sorted data
O(n)
say "oh of n"		 Linear. Look at each of the n items once. Double n → double the work. for x in list · sum(list)
O(n log n)
say "oh n log n"		 For each of n items, do log n work. This is what sorting costs. sorted(list)
O(n²)
say "oh of n squared"		 Pairs. For each item, look at every OTHER item = n × n. Double n → 4× the work. Nested loop over same list
O(2ⁿ)
say "oh two to the n"		 Every subset. The little ⁿ means the number 2 multiplied by itself n times (2 × 2 × 2 × …). Each extra item DOUBLES the work. n = 60 → longer than the age of the universe. Brute-force "try every combination"
O(n!)
say "oh of n factorial"		 Every possible order. The ! is the maths symbol for factorial — it means multiply n by every smaller whole number down to 1: 5! = 5 × 4 × 3 × 2 × 1 = 120. So 15! ≈ 1.3 trillion. Doesn't run on any real hardware. Naive travelling-salesman
"But why log n? Why not something scarier?" Because log₂(n) literally answers: "how many times can I halve n before I reach 1?" That's the definition of log base 2. n = 1,024 → 10 halvings. n = 1M → 20. n = 1B → 30. Doubling n only adds ONE more step — which is why O(log n) is almost as good as O(1).

"Why n² and not n log n?" Because the algorithm does n work × n more work, not n × log n. The name describes what happens — it's not a formula to memorize.

Why is it called "Big-O"? A 30-second history

Last mystery — why the name "Big-O" and not "alpha-O" or something else?

The origin — one line The letter O stands for the German word Ordnung — "order of", as in "on the order of magnitude". Coined by German mathematician Paul Bachmann in 1894 to describe how math functions grow. Picked up for computer science by Donald Knuth in 1976 to describe how algorithms scale. That's the whole story. The letter itself doesn't matter — if a French mathematician had invented it, we'd be saying "Grand-O" today.
"Why BIG O? Are there other O's?" Yes — Bachmann's original family had three notations for how a function grows. Here's the whole set:
Notation Read as What it means When you'll see it
O(f) "Big-O of f" Upper bound — grows at most this fast (the worst case) 99% — code reviews, interviews, docs
Ω(f) "Big-Omega of f" Lower bound — grows at least this fast (the best case) Rare — academic proofs
Θ(f) "Big-Theta of f" Tight bound — grows exactly this fast (worst = best) Rare — precise algorithm analysis
In real engineering conversations, everyone just says "Big-O" and means "the worst case". You'll never hear a colleague say "this is Big-Theta of n log n" in a code review. Knowing Big-O covers 99% of what you need.
The one takeaway Read "O(n²)" out loud as "on the order of n squared operations". That's it. Big-O isn't a formula or magic — it's a label for how an algorithm's cost grows with its input. Chapter 1 done. Now let's use these words to describe real code.

Two functions, same answer, ~100,000× time gap — the vocabulary in action

You now know the words. Let's use them on real code. Here are two Python functions. They take the same input. They return the same correct answer. On a list of 10 items you cannot tell them apart — both feel instant. But as the input grows, the growth patterns you just learned about start to pull apart.

Version A

Do the numbers contain any duplicate?

def has_duplicate_slow(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False
Version B

Do the numbers contain any duplicate?

def has_duplicate_fast(nums):
    seen = set()
    for n in nums:
        if n in seen:
            return True
        seen.add(n)
    return False

Run it yourself — paste this whole block into main.py

import random, time

def has_duplicate_slow(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]: return True
    return False

def has_duplicate_fast(nums):
    seen = set()
    for n in nums:
        if n in seen: return True
        seen.add(n)
    return False

nums = random.sample(range(10_000_000), 20_000)   # 20k unique ints — no duplicates

for name, fn in [("slow", has_duplicate_slow), ("fast", has_duplicate_fast)]:
    t = time.perf_counter()
    fn(nums)
    print(f"{name}: {(time.perf_counter() - t) * 1000:.1f} ms")

# Expected output on a laptop (numbers vary by machine, ratio doesn't):
# slow: ~1000-3000 ms
# fast: ~1 ms
# → same input, same answer, ~1,000× time difference

Same output. Both correct. Both readable. But measure them on lists of increasing size and you get this pattern on any machine:

Input size (n) Version B — fast Version A — slow B is faster by…

The absolute numbers depend on your laptop. The ratios — the growth pattern — are the same on every machine on Earth. That's what "complexity" describes.

Same picture as a chart — see how quickly the two curves pull apart:

Version A is O(n²). Version B is O(n). At n = 1M, that's the difference between an API endpoint that responds in 25 ms and one that never responds at all.

This is not a made-up example — it actually happens This exact bug — if x in list inside a loop — is the single most common speed bug in real Python code. It works fine in dev on 100 rows. It passes code review. It ships. Then production hits real data, an endpoint stops responding, and the on-call engineer gets paged in the middle of the night.
The skill this lesson gives you Both functions look clean. Both are correct. But being able to see — just by reading the code, without running it — that Version A gets 100,000× slower as data grows and Version B stays fast, is exactly what separates a junior developer from a senior one. That skill has a name: Big-O thinking. Chapter 2 done. Chapter 3 · The rules & the seven curves

The rules of Big-O — drop constants, keep the dominant term

Three simple rules turn any messy formula into a clean Big-O label. But first: where does that formula even come from? You count operations in the code, block by block. Once you have the total, the rules throw away the noise and leave you with the Big-O.

What counts as ONE step? (and yes — an if is just one step) Almost every single line of code = O(1), one step. That covers: assignments (x = 5), arithmetic (a + b), comparisons (x < y), dict/set lookups (d[k], k in s), list indexing (lst[i]), a function call like len(lst), and — the one people ask about — an if check. An if by itself is one comparison, so O(1). An if only becomes O(n) when it lives inside a loop that runs n times — and even then, the LOOP is doing the O(n) work, not the if.
What makes a loop O(n)? A loop that runs n times (where n depends on input size) turns everything inside it into n × (cost of the body). If the body is O(1), the loop is O(n). If the body contains another loop of size n, you get n × n = O(n²). That is the whole game — Big-O is basically counting how many times your loops run.

Concrete example — count first, then apply the rules

Here's a small function that counts even numbers in a list. It has a setup, a loop, an if inside the loop, and a return. Let's count every step:

def count_evens(nums):
    total = 0                    # 1 step   (setup)
    n = len(nums)                # 1 step   (setup)
    for num in nums:             # loop runs n times ↓
        if num % 2 == 0:         #   1 step per pass  (the if check)
            total = total + 1    #   1 step per pass  (only when even)
    return total                 # 1 step   (return)

# ── try it ──
print(count_evens([1, 2, 3, 4, 5, 6]))   # → 3

Add it up. Setup = 2 steps. Loop runs n times, doing up to 2 steps per pass (the if plus the total = total + 1). Return = 1 step. Total: 2 + 2n + 1 = 2n + 3 steps. Now the rules turn that into a clean label.

The three rules — all of Big-O notation 1. Drop constants: O(2n + 3) becomes O(n). The "2" (two things done inside the loop) and the "3" (setup + return) depend on the exact code and the exact machine — not on how the algorithm grows. Only the n tells us the growth pattern.
2. Keep only the dominant term: O(n² + 100n + 500) becomes O(n²). At large n, the biggest term drowns everything else.
3. Report the worst case: unless asked otherwise, "the complexity" = the slowest case on the meanest input.

Applying rule 1 to count_evens: 2n + 3 → O(n). That's the answer. Even though the function has a setup, an if, an assignment inside the loop, and a return — the one loop over n items is the only thing that controls how the work grows.

Why we drop constants and small terms — the numbers

Still feel weird throwing away the "2" and the "3"? Watch what happens as n gets big. Compare Algorithm A doing 3n + 100 steps vs Algorithm B doing 0.5n²:

nA: 3n + 100B: 0.5n²Winner
1013050B
1,0003,100500,000A (by 160×)
1,000,0003M500 billionA (by 167,000×)

The 0.5, the +100, even the ×3 — none of them matter at scale. All that matters is the exponent on n. That is exactly why we call these simply O(n) and O(n²) — the Big-O throws away the noise and keeps the shape.

Best · average · worst — always report the worst Some algorithms behave very differently on different inputs: quicksort is O(n log n) average but O(n²) worst-case (bad pivot). Dict lookup is O(1) average but O(n) worst-case (hash collisions — almost never happens in practice). When asked "what's the complexity?", answer with the worst case. That's the number that matters when your code hits production data you cannot predict.

O(1) — constant time · "same speed forever"

Same time whether the collection has 10 elements or 10 billion. The fastest complexity class that exists.

# Dict / set lookup — O(1)
scores = {"Alice": 95, "Bob": 87}
score = scores["Alice"]      # instant, whether dict has 2 or 2 million entries
exists = "Bob" in scores    # hash lookup — instant, regardless of size

# List operations at the end — O(1)
items = []
items.append("x")               # adding to end is instant
first = items[0]                 # direct memory jump by index

# ── try it ──
print(score, exists, first)     # → 95 True x
Why hash lookup is O(1) A hash function converts "Alice" into a number, and that number tells Python exactly where in memory to look. No scanning. This is the entire reason dict and set exist as separate types from list.

What's O(1) in Python

O(log n) — logarithmic · "cut the problem in half"

Every step throws away half the remaining data. Doubling n only adds ONE extra step — nearly as good as O(1) even on billions of items.

def binary_search(sorted_list, target):
    low, high = 0, len(sorted_list) - 1
    while low <= high:
        mid = (low + high) // 2
        if sorted_list[mid] == target:
            return mid
        elif sorted_list[mid] < target:
            low = mid + 1        # throw away the lower half
        else:
            high = mid - 1       # throw away the upper half
    return -1

# ── try it ──
nums = list(range(1, 1_000_001))               # sorted 1..1M
print(binary_search(nums, 742_913))          # → 742912 (found in ~20 steps)
print(binary_search(nums, -1))                 # → -1  (not there)

O(n) — linear · "look at every item once"

Work scales in direct proportion to the input — double n, double the time. The honest baseline for any problem that must look at all the data.

def find_max(numbers):
    maximum = numbers[0]
    for num in numbers:      # visits every element exactly once
        if num > maximum:
            maximum = num
    return maximum

# ── try it ──
print(find_max([3, 1, 4, 1, 5, 9, 2, 6]))     # → 9

What's O(n) in Python

for x in list sum/min/max(list) x in list · linear scan! list.count/index(x) set(list) · building Counter(iterable)
O(n) is the sweet spot You can't do better than O(n) when you genuinely need to look at every item. A "clean O(n) solution" is often the correct target — going faster requires skipping data (impossible for many problems) or precomputing (which costs its own time). Two O(n) operations in a row is still O(n). What kills you is O(n) inside another O(n) — that's O(n²).

Chapter 4 · The four you use daily

O(n log n) — linearithmic · "the price of sorting"

Slightly slower than linear, still totally practical at scale. This is the complexity of every good comparison sort — Python's sorted() uses Timsort, which is O(n log n).

numbers = [3, 1, 4, 1, 5, 9, 2, 6]
sorted_nums = sorted(numbers)      # O(n log n) — Timsort, returns a NEW list
numbers.sort()                     # O(n log n) — sorts in-place

# ── try it ──
print(sorted_nums)                  # → [1, 1, 2, 3, 4, 5, 6, 9]
print(numbers)                      # → [1, 1, 2, 3, 4, 5, 6, 9]  (mutated)
Why sorting is n log n Any comparison sort must compare each of n elements to about log n others to place it. Total: n × log n. This is a proven mathematical lower bound — you cannot sort by comparisons any faster. On 1M items = ~20M ops = ~200 ms on a laptop.
The subtle O(n² log n) trap Calling sorted() inside a loop over the same data turns O(n log n) into O(n² log n). Always sort once, outside the loop.

O(n²) — quadratic · the danger zone (and beyond)

Time grows with the square of the input. Double n → 4× work. 10× n → 100× work. This is where most real-world performance bugs live.

def has_duplicate_slow(items):
    for i in range(len(items)):          # n iterations
        for j in range(i + 1, len(items)): # ~n iterations (nested)
            if items[i] == items[j]:
                return True
    return False
# n = 100 → 5,000 ops. n = 1,000 → 500,000. n = 100,000 → 5 BILLION (minutes).

# ── try it ──
print(has_duplicate_slow([1, 2, 3, 4, 2]))   # → True
print(has_duplicate_slow([1, 2, 3, 4, 5]))   # → False
Rule of thumb Any nested loop over the same input is a red flag. Not always wrong (matrix math genuinely needs it), but it should trigger the question: can I use a set/dict/sort to skip that inner loop?

Beyond quadratic — you'll never write these on purpose

O(2ⁿ) exponential — every element doubles the work. Classic trap: recursive Fibonacci without memoization dies at n ≈ 35. O(n!) factorial — every permutation. Naïve travelling salesman. At n = 40, an O(2ⁿ) algorithm already takes minutes. The fix is almost always @functools.cache:

Run it yourself — feel the exponential vs. linear difference

import time
from functools import cache

# EXPONENTIAL — O(2ⁿ), dies at n ≈ 35
def fib_slow(n):
    if n < 2: return n
    return fib_slow(n-1) + fib_slow(n-2)

# LINEAR — one decorator collapses it to O(n)
@cache
def fib_fast(n):
    if n < 2: return n
    return fib_fast(n-1) + fib_fast(n-2)

t = time.perf_counter(); fib_slow(32); print(f"fib_slow(32): {(time.perf_counter()-t)*1000:.0f} ms")
t = time.perf_counter(); fib_fast(500); print(f"fib_fast(500): {(time.perf_counter()-t)*1000:.3f} ms")

# Expected on a laptop (varies by machine, ratio doesn't):
# fib_slow(32):  ~100-500 ms   ← doubles every +1 to n. Try 35 → seconds. 40 → minutes.
# fib_fast(500): under 1 ms    ← handles 15× bigger n, almost free

Chapter 5 · Space complexity

What space complexity is — the other half of Big-O

Everything so far measured time. Space complexity measures the extra memory your algorithm needs beyond the input itself — using the exact same notation. Same rules, same intuition.

O(1) space — a few variables, never grows 
def find_max(nums):
    m = nums[0]        # 1 variable
    for n in nums:
        if n > m: m = n
    return m
# O(n) time, O(1) space

# ── try it ──
print(find_max([3, 7, 2, 9, 4]))  # → 9
O(n) space — extra container scales with input 
def deduplicate(items):
    seen = set()          # grows up to n
    out = []               # grows up to n
    for x in items:
        if x not in seen:
            seen.add(x); out.append(x)
    return out
# O(n) time, O(n) space

# ── try it ──
print(deduplicate([1, 2, 1, 3, 2, 4]))  # → [1, 2, 3, 4]
Time and space are INDEPENDENT — always answer as a pair Code can be O(n) time / O(1) space (a scan with counters), O(n) time / O(n) space (building a set), or O(n²) time / O(1) space (nested loops that only compare). Strong answer = "O(?) time, O(?) space" — both halves.

Chapter 5 · Space complexity

O(1) · O(n) · O(n²) space — the three classes you'll see

The dangerous one is O(n²) space — one 2D structure sized by the input:

# Distance matrix between every pair of points — O(n²) space
def all_pair_distances(points):
    n = len(points)
    matrix = [[0] * n for _ in range(n)]    # n × n cells
    for i in range(n):
        for j in range(n):
            # distance between two (x, y) points
            dx, dy = points[i][0] - points[j][0], points[i][1] - points[j][1]
            matrix[i][j] = (dx * dx + dy * dy) ** 0.5
    return matrix               # O(n²) time AND O(n²) space

# ── try it ──
pts = [(0, 0), (3, 4), (6, 8)]
for row in all_pair_distances(pts):
    print([round(x, 1) for x in row])
# → [0.0, 5.0, 10.0]
# → [5.0, 0.0, 5.0]
# → [10.0, 5.0, 0.0]
The physical wall — space bugs CRASH, they don't run slowly 1M items × 1M cells × 8 bytes = 8 terabytes of RAM. Your laptop has 16 GB. O(n²) space simply cannot run on real data — MemoryError before the algorithm finishes.
Don't forget: recursion depth is space too Every recursive call adds a stack frame. Recursion that goes n levels deep = O(n) space even if it allocates nothing. Converting recursion to iteration often collapses O(n) space back to O(1).

Chapter 5 · Space complexity

Time ↔ space tradeoff — the most useful engineering lever

The deepest idea in this whole lesson: time and space are exchangeable. Spend memory to save time (caching), or spend CPU to save memory (streaming). Seeing this lever is what makes you an engineer.

Direction 1 — Trade space for time (memoization)

Fibonacci recursion recomputes the same subproblems billions of times. Store them once:

O(2ⁿ) time — dies at n ≈ 35 
def fib_slow(n):
    if n < 2: return n
    return fib_slow(n-1) + fib_slow(n-2)

# ── try it ──
print(fib_slow(10))     # → 55
print(fib_slow(30))     # → 832040 (~1 sec — try 35!)
O(n) time — handles n = 100,000 
from functools import cache
@cache
def fib_fast(n):
    if n < 2: return n
    return fib_fast(n-1) + fib_fast(n-2)

# ── try it ──
print(fib_fast(100))    # → 354224848179261915075 (instant)

Direction 2 — Trade time for space (streaming)

Reading a huge file. Loading it all is O(n) space. Streaming line-by-line is O(1) space:

O(n) space — crashes on 10 GB log 
with open("huge.log") as f:
    lines = f.readlines()   # entire file into RAM
    errors = [l for l in lines if "ERROR" in l]
O(1) space — any file size 
errors = []
with open("huge.log") as f:
    for line in f:        # one line at a time
        if "ERROR" in line:
            errors.append(line)

To try this: create a small huge.log file with a few lines containing "ERROR", then run either version.

The engineering rule of thumb Spend memory to save time — until you can't afford the memory. RAM is cheap, wall-clock is expensive. "Trade space for time" is the default lever (this is what Redis, CDNs, DB indexes, and memoized ML pipelines all do). Reverse it only when input threatens memory (huge files, streaming data, embedded systems).

Chapter 6 · Five traps

Trap 1 — x in list inside a loop

The most common O(n²) bug in production Python. Even experienced developers write it without thinking.

The task Given two lists, return every element that appears in both lists. Example: find_common([1, 2, 3, 4], [3, 4, 5, 6]) → [3, 4]. A student would naturally reach for the left-hand code. Read on for why that's the trap.
O(n²) — trap 
def find_common_slow(list1, list2):
    common = []
    for item in list1:      # O(n)
        if item in list2:    # O(m) — list scan!
            common.append(item)
    return common
# Total: O(n × m) ≈ O(n²)
O(n) — fix 
def find_common_fast(list1, list2):
    set2 = set(list2)          # O(m) once
    return [x for x in list1 if x in set2]
# O(n + m). Linear.

Run it yourself — see the ~1,000× speed-up

import random, time

def find_common_slow(list1, list2):
    return [x for x in list1 if x in list2]     # O(n × m)

def find_common_fast(list1, list2):
    set2 = set(list2)
    return [x for x in list1 if x in set2]     # O(n + m)

list1 = random.sample(range(100_000), 10_000)
list2 = random.sample(range(100_000), 10_000)

for name, fn in [("slow", find_common_slow), ("fast", find_common_fast)]:
    t = time.perf_counter()
    fn(list1, list2)
    print(f"{name}: {(time.perf_counter() - t) * 1000:.1f} ms")

# Expected on a laptop (numbers vary, ratio doesn't):
# slow: ~300-1500 ms
# fast: under 2 ms  ← ~500-1000× faster from ONE line: list → set
Same syntax, wildly different cost x in something looks instant. But in on a list/tuple scans every element = O(n). On a set/dict it hashes = O(1). The reflex: whenever you see if x in Y: inside a loop, ask "is Y a set or dict? If not, why not?"

Chapter 6 · Five traps

Trap 2 — Nested loops when a set / dict would work

Any time you're comparing every element against every other element ("does this pair exist?"), a hash-based structure collapses O(n²) → O(n).

The task Given a list of numbers and a target sum, return the indices of the two numbers that add up to the target. Example: two_sum([2, 7, 11, 15], 9) → (0, 1) (because 2 + 7 = 9). The natural "check every pair" answer on the left is O(n²) — the right side does it in one pass.
O(n²) — two-sum, brute force 
def two_sum_slow(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return (i, j)

# ── try it ──
print(two_sum_slow([2, 7, 11, 15], 9))  # → (0, 1)
O(n) — with a hash map 
def two_sum_fast(nums, target):
    seen = {}                # value → index
    for i, n in enumerate(nums):
        if (target - n) in seen:
            return (seen[target - n], i)
        seen[n] = i

# ── try it ──
print(two_sum_fast([2, 7, 11, 15], 9))  # → (0, 1)
The interview trick behind this They're not testing whether you can write nested loops. They're testing whether you can invert the search: instead of "for every pair, check if it works", rephrase to "for each element, have I already seen its partner?" That reframe powers duplicate detection, first-unique-character, anagram grouping, longest substring without repetition, and dozens of others.

Chapter 6 · Five traps

Trap 3 — String concatenation with += in a loop

Strings in Python are immutable. Every += creates a whole new string and copies every character across. Over n iterations, that's 1+2+...+n = n(n+1)/2 character copies = O(n²).

The task Join a list of words into one space-separated string. Example: ["one", "two", "three", "four"] → "one two three four ". Beginners reach for the += loop on the left — which sneaks in an O(n²) copy every iteration.
O(n²) — trap 
words = ["one", "two", "three", "four"]
result = ""
for word in words:
    result += word + " "   # new string each iteration
print(result)               # → "one two three four "
O(n) — fix 
words = ["one", "two", "three", "four"]
result = " ".join(words) + " "  # one allocation
print(result)               # → "one two three four "
Same trap in disguise tuple += (x,), repeated bytes concatenation, chained list1 + list2 + list3 — all hit the same "immutable → O(n²) copy" wall. Always: collect into a list, then join or convert at the end.

Chapter 6 · Five traps

Trap 4 — Sorting when you only need the extreme

You want the smallest item (or top 3). The wasteful reflex is to sort everything.

The task Given a list of numbers, return the smallest value and the 3 smallest values. Example: [42, 7, 99, 3, 51, 18] → smallest = 3, top-3 smallest = [3, 7, 18]. The trap on the left sorts the whole list even though you only need the tail — the right side uses the exact tool for the job.
O(n log n) — waste 
numbers = [42, 7, 99, 3, 51, 18]
smallest = sorted(numbers)[0]     # sorts everything
top_3    = sorted(numbers)[:3]    # sorts everything
print(smallest, top_3)          # → 3 [3, 7, 18]
O(n) — right tool 
import heapq
numbers = [42, 7, 99, 3, 51, 18]
smallest = min(numbers)              # O(n)
top_3 = heapq.nsmallest(3, numbers) # O(n log k)
print(smallest, top_3)          # → 3 [3, 7, 18]
Don't do more than the problem asks Sorting arranges every element relative to every other. For the extreme, top-k, or "is it sorted?" — use min, max, heapq.nsmallest/nlargest, bisect. On top-10 from 1M items, nsmallest is dramatically faster than a full sort.

Chapter 6 · Five traps

Trap 5 — Hidden O(n²) in one-liners & comprehensions

Comprehensions look tight but hide loops. If a comprehension calls an O(n) function on each element, it silently becomes O(n²).

The task Given a list, return every item that appears more than once (each duplicate kept every time it shows up). Example: [1, 2, 3, 2, 4, 3, 5] → [2, 3, 2, 3]. The one-liner on the left looks clean but calls an O(n) helper inside the comprehension — a hidden O(n²).
O(n²) — hidden 
items = [1, 2, 3, 2, 4, 3, 5]
duplicates = [x for x in items if items.count(x) > 1]
#                                  ^^^^^ items.count is O(n)!
print(duplicates)   # → [2, 3, 2, 3]
O(n) — fix 
from collections import Counter
items = [1, 2, 3, 2, 4, 3, 5]
counts = Counter(items)             # O(n) once
duplicates = [x for x in items if counts[x] > 1]
print(duplicates)   # → [2, 3, 2, 3]
Rule of thumb for one-liners A comprehension's Big-O is (items) × (cost of the expression per item). If the expression calls count, index, x in list, or any helper that iterates, that expression is O(n) — and the comprehension is O(n²). Look inside the brackets, not just at them.
The 5 traps summed up These five are 90% of real-world Python performance bugs — in list in a loop, nested loops that should be a set, string += that should be join, sorted when you needed min, and comprehensions that look linear but aren't. Recognise these and you've eliminated most future outages.

Chapter 7 · Data structures cheat sheet

The right data structure kills the algorithm

The biggest performance wins don't come from clever algorithms. They come from noticing "this problem is O(n²) with a list, but O(n) with a set." Two examples that show up in every codebase:

Example 1 — Removing duplicates while preserving order

O(n²) — x not in result is O(n)! 
items = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3]
result = []
for item in items:
    if item not in result:  # scans result!
        result.append(item)
print(result)   # → [3, 1, 4, 5, 9, 2, 6]
O(n) — set for lookups, list for order 
items = [3, 1, 4, 1, 5, 9, 2, 6, 5, 3]
seen, result = set(), []
for item in items:
    if item not in seen:    # O(1)
        seen.add(item)
        result.append(item)
print(result)   # → [3, 1, 4, 5, 9, 2, 6]

Example 2 — Sliding window over a stream

O(n²) — list.pop(0) shifts everything 
stream = [1, 2, 3, 4, 5, 6, 7, 8]
k, window = 3, []
for item in stream:
    window.append(item)
    if len(window) > k:
        window.pop(0)          # O(n)!
    print(window)
# → [1] [1,2] [1,2,3] [2,3,4] [3,4,5] ...
O(n) — deque, both ends O(1) 
from collections import deque
stream = [1, 2, 3, 4, 5, 6, 7, 8]
window = deque(maxlen=3)   # auto-drops old
for item in stream:
    window.append(item)      # O(1)
    print(list(window))
# → same output, ~1,000× faster on 1M-item streams
The senior habit — refuse the wrong container When you catch yourself writing a nested loop, an x in list, or a list.pop(0) — stop. Ask: "am I using the wrong container?" Changing one list to a set/dict/deque often collapses the complexity by a whole order.

Chapter 8 · Interview patterns

Two-sum — the pattern every top-tier interview tests

Given a list of numbers and a target, find two numbers that add up to it. Possibly the most-asked interview question — it separates candidates who see O(n) from those who write nested loops.

O(n²) — brute force 
def two_sum(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return (i, j)

# ── try it ──
print(two_sum([2, 7, 11, 15], 9))   # → (0, 1)
print(two_sum([3, 2, 4], 6))          # → (1, 2)
O(n) time · O(n) space — the trick 
def two_sum(nums, target):
    seen = {}    # value → index
    for i, n in enumerate(nums):
        if (target - n) in seen:
            return (seen[target - n], i)
        seen[n] = i

# ── try it ──
print(two_sum([2, 7, 11, 15], 9))   # → (0, 1)
print(two_sum([3, 2, 4], 6))          # → (1, 2)
The senior answer, out loud "Naïvely I'd try every pair — O(n²) time, O(1) space. But I can trade some space to get down to O(n): as I walk the list once, for each number I check if its complement target - n has already been seen — dict lookup, O(1). That's O(n) time and O(n) space. It's the classic 'invert the search' trick."
The follow-up trap Interviewer: "OK, now what if the list is sorted?" The hash-map still works, but there's now an O(1) space solution with two pointers (one at each end, walk inward). Same family as "3-sum" and "container with most water". Recognising when input structure lets you switch strategies is what they test next.

Chapter 8 · Interview patterns

The other patterns — duplicates & frequencies

Once you internalise the hash-map trick from two-sum, this whole family collapses into one-liners.

Pattern A — Duplicate detection

def has_duplicate(nums):
    return len(set(nums)) < len(nums)   # O(n)

# ── try it ──
print(has_duplicate([1, 2, 3, 2]))       # → True
print(has_duplicate([1, 2, 3, 4]))       # → False

Pattern B — Word / element frequency

from collections import Counter

words = "the quick brown fox jumps over the lazy dog the fox".split()
counts = Counter(words)                     # O(n) — tf-idf, log analysis, tallies
top_3 = counts.most_common(3)               # O(k log 3)

print(counts["the"])                        # → 3
print(top_3)                                # → [('the', 3), ('fox', 2), ('quick', 1)]
The shared pattern behind all of them Every problem in this family is "walk the input once and remember the right thing". The "right thing" is either a set (seen? yes/no) or a Counter/dict (seen how many times?). Once you recognise this shape — duplicate detection, first-unique-character, anagram grouping, longest-substring-without-repetition — you go straight to O(n). No nested loops, no confusion.

Chapter 9 · Analyse your own code

The 4-step method — work out the Big-O of any function in 30 seconds

Given code you didn't write, how do you tell its Big-O? Four steps, always same order.

STEP 1 · COUNT NESTED LOOPS OVER THE INPUT │ 1 loop → O(n) · 2 nested → O(n²) · 3 nested → O(n³) ▼ STEP 2 · WHAT LIVES INSIDE THE LOOPS? │ Constant work (arithmetic, dict lookup) → multiplies by 1 │ Another O(n) call (list `in`, sort, sum) → multiplies by n │ Recursion → treat as another loop ▼ STEP 3 · HIDDEN WORK OUTSIDE THE LOOPS? │ `sorted(data)` before the loop → adds O(n log n) │ I/O (file read, DB query) → often the real bottleneck ▼ STEP 4 · DROP CONSTANTS, KEEP THE DOMINANT TERM │ O(n) + O(n log n) = O(n log n) · O(n²) + O(n) = O(n²) ▼ YOU HAVE THE BIG-O

Worked example — walk the method through a real function

def group_by_first_letter(words):
    words = sorted(words)                        # [A] O(n log n)
    groups = {}
    for w in words:                             # [B] loop × n
        first = w[0]                              # [C] O(1)
        if first not in groups:                   # [D] O(1) dict
            groups[first] = []
        groups[first].append(w)                     # [E] O(1)
    return groups

# ── try it ──
print(group_by_first_letter(["apple", "banana", "avocado", "blueberry", "cherry"]))
# → {'a': ['apple', 'avocado'], 'b': ['banana', 'blueberry'], 'c': ['cherry']}

Add it up: [A] O(n log n) outside + [B]×([C]+[D]+[E]) = n × O(1) = O(n) inside. Total: O(n log n) + O(n) = O(n log n). Space: O(n) for the dict.

Common analysis mistakes 1. Counting x in list as O(1). It's O(n) unless it's really a set/dict.
2. Assuming sorted() in a loop only sorts once — it re-sorts every iteration = O(n² log n).
3. Ignoring recursion depth as space. A function that recurses n deep uses O(n) stack even if it allocates nothing.

The senior-answer template — state Big-O out loud

When asked "what's the complexity of this?" — in a code review, a design doc, or an interview — the strong answer follows this 4-part shape:

The 4-part template 1. Time & space (as a pair). "O(?) time and O(?) space because…"
2. Worst case. "In the worst case [condition], it degrades to [worse Big-O]." (If applicable.)
3. Practical impact. "At our real data size, that's [ms / seconds / crash]."
4. Alternative & tradeoff. "If [X] becomes a bottleneck, we can improve to O(?) by [technique] at the cost of [what]."

Walk-through — using the template on two-sum

Chapter 10 · The payoff · Loop closed

The answer — remember the opening experiment?

Back in Chapter 2, two functions gave the same answer. One took milliseconds. One took hours. You didn't have the vocabulary yet. Now you do.

Version A — the slow one 
def has_duplicate_slow(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False
Version B — the fast one 
def has_duplicate_fast(nums):
    seen = set()
    for n in nums:
        if n in seen:
            return True
        seen.add(n)
    return False
You can now say this in one breath Version A is O(n²) time, O(1) space — two nested loops, no extra memory. Version B is O(n) time, O(n) space — one pass, using a set for O(1) lookup. Version B spends O(n) extra memory to save O(n²) → O(n) time. At n = 1M, that's the difference between 25 milliseconds and 4 hours.
The whole lesson in one paragraph Complexity is growth with input size, not wall-clock speed (Ch 1). Big-O is a compact label for that growth — apply three rules (drop constants, keep the dominant term, report the worst case) and only seven curves matter; past O(n²) the algorithm can't practically run (Ch 3–4). Every algorithm has BOTH time AND space complexity, and you can trade one for the other (Ch 5). Five specific traps cause 90% of real-world Python performance bugs (Ch 6). Data-structure choice — list vs dict/set/deque — kills whole classes of complexity (Ch 7). The two-sum family collapses to "walk the input once, remember the right thing" (Ch 8). Given any function, count loops → check what runs inside → drop constants → done (Ch 9). That is Big-O thinking.

Where this shows up in your career

API latency: O(n²) endpoint dies at scale — every scale-related outage is a Big-O story Database indexes: full-scan is O(n), indexed lookup is O(log n) — that's why indexes exist Data pipelines: O(n²) join on 10M rows never finishes — streaming/hashing → O(n log n) Front-end: React list that re-renders O(n²) per keystroke feels laggy — memoisation → O(n)
